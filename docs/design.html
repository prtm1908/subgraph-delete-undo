Undo in a Shared Graph

Undo in a Shared Graph

A command-line tool that keeps a graph in one SQLite file and can take back a subtree delete after other people and an ingest job have kept working on the same graph. This page covers the parts of the tool, how the graph sits in SQLite, and how undo decides what to bring back.

The situation it is built for: many people and several automated jobs edit one large graph at the same time. One person bulk-deletes a subtree of about 10,000 nodes. Twenty minutes later, after others have made several hundred edits in and around that area, the same person asks for the delete to be taken back. The tool is that design scoped down to one process, and the example below is the same story with six nodes.

1Architecture

There are no services to run. The task fixes the tool to one process and one database file, so the picture is one Python program with a few parts inside it, one SQLite file next to it, and two small helper programs outside it.

The parts and what each one does

Python 3.11+
The language. Its standard library already includes SQLite (sqlite3), JSON, UUIDs and a command-line parser, so nothing has to be installed.
graph.db
One SQLite file. It holds the live graph and the journal. SQLite features used: transactions, foreign keys, unique indexes, and recursive queries.
load
Loader. Starts a new database file, replacing an old one. Reads seed.jsonl and fills the nodes and edges tables, then computes tags once for the whole graph.
apply
Operation applier. Runs ops.jsonl in order. Five kinds of operation: edit a node, add an edge, re-point an edge, ingest a node by name, delete a subtree. Each is described under "What can change the graph" below. When ingest creates a node, its id is built from the op_id and the name, so the same files give the same ids on every run. A delete moves what it removes into the journal. A contains arrow that would make a node its own ancestor is refused: the operation is stored as rejected and changes nothing, so a loop never gets into the graph. The same happens to an operation that names a node or arrow that is not live. An op_id names one operation: when it is already in the database, the line is skipped if it is that same operation, so applying a file again is harmless, and apply stops with an error before changing anything if it is a different one.
undo <op_id>
Undo engine. Walks the journal rows of one delete, decides restored, merged or skipped for each, writes the result, prints the report. It only accepts the op_id of a subtree delete. For any other operation, or an id that does not exist, it prints an error and writes nothing.
dump
Dumper. Prints every live node and edge as JSONL in one fixed order: node lines sorted by id, then edge lines sorted by from, to and type. Keys are always in the same order, inherited tags are sorted alphabetically, and own tags stay in the order they were written. Two equal graphs always print the same bytes. A node line holds id, qualified_name, type, description, owner, tags and effective_tags. An edge line holds from_id, to_id and type.
Tag propagator
One function: recompute inherited tags for a node and everything below it. Called by apply and by undo.
Store
A thin layer over sqlite3. Opens the file, turns foreign keys on, wraps each step in a transaction, and counts write statements so CRASH_AFTER=<n> can stop the process on the n-th one.
gen_fixture.py
Makes seed.jsonl and ops.jsonl from a seed number, and planted.json, which lists the nodes each planted case uses. Same seed, same files: every id and every choice comes from one random generator started with the seed. It checks its own output against the minimums the task sets and stops with an error if one is missed.
checker.py
A separate program that imports nothing from the tool. It replays the seed and the operations in plain Python dictionaries, then compares that with the dumps and the report for the eight checks, and for the redo checks in section 4.

What can change the graph

These are all the kinds of change the tool knows. Every one carries who made it: a person or the ingest.

Edit a node
By a person. Sets the description, the owner or the tags of one live node. A tag change is passed down to everything the node contains. An edit from ingest is refused, because ingest never sets description, owner or tags.
Add an arrow
By a person or by ingest. Adds a contains or references arrow between two live nodes.
Re-point an arrow
By a person or by ingest. Moves one end of an existing arrow to another node. It counts as two changes: the old arrow is taken away and the new one is added. Re-pointing a contains arrow moves a node under another parent.
Ingest a node by name
By ingest. If a live node already has the name, ingest updates its type. If none has it, ingest creates a node with a new id and puts it under its parent, if that parent is live. Ingest never sets description, owner or tags. An ingest from a person is refused: people do not create nodes in this tool, and only ingest sets the type.
Delete a subtree
By a person or by ingest. Removes a node, everything it contains, and every arrow that touches any of them. The inherited tags of the nodes that remain are then recomputed.
Undo a delete
By a person, with the undo command. It takes the op_id of one subtree delete. The undo is recorded as an operation of its own, so a redo can tell what came after it.
Redo a delete
By a person, with the redo command, the one extension to the task's four commands. It takes the op_id of a subtree delete that has been undone, and takes back what the undo put back. Section 4 describes it.

Not part of the tool: a person creating a node, renaming a node, removing a single arrow without re-pointing it, undoing anything other than a subtree delete, the 24-hour limit, and checking who is allowed to do what.

2The graph inside SQLite

SQLite stores tables, not graphs. A graph is two lists: a list of things and a list of arrows between them. So there are two tables. Each row in nodes is one box. Each row in edges is one arrow, written as "from this id, to that id, of this kind".

The running example is a small data catalog. Ids are shortened to n1, n2 and so on; the real ones are UUIDs.

Tags that flow down from a parent

The task calls them tags. A tag set on a parent is carried by every node below it. A node has two tag columns. tags is what someone set on that node. effective_tags is worked out: the node's own tags plus the effective tags of its parent. In the table above, sales.orders.email has one tag of its own and gets pii and finance from the two nodes above it. Only contains arrows carry tags. references arrows do not.

Walking the graph

"Everything under sales.orders" is found by a recursive query. Start with the root. Add every node it contains. Add every node those contain. Stop when a round adds nothing.

WITH RECURSIVE sub(id) AS (
    SELECT :root_id
  UNION
    SELECT e.to_id
    FROM edges e JOIN sub ON e.from_id = sub.id
    WHERE e.type = 'contains'
)
SELECT id FROM sub;

The query uses UNION, which drops a node it has already found, so the walk always ends. This matters if a contains loop ever exists, for example A contains B and B contains A. With UNION ALL, or with a depth counter inside the query, the walk goes round the loop for ever. The parents-first order that undo needs is worked out afterwards, by following the removed contains arrows down from the root.

The same walk, run downward from a node, is how the tag propagator refreshes effective_tags for a subtree: each node takes its own tags plus the already-refreshed tags of its parent.

The tables

CREATE TABLE nodes (
  id              TEXT PRIMARY KEY,
  qualified_name  TEXT NOT NULL UNIQUE,   -- this table holds live nodes only
  type            TEXT NOT NULL,
  description     TEXT,
  owner           TEXT,
  tags            TEXT NOT NULL,          -- JSON list, set by people
  effective_tags  TEXT NOT NULL           -- JSON list, worked out
);
CREATE TABLE edges (
  from_id TEXT NOT NULL REFERENCES nodes(id),
  to_id   TEXT NOT NULL REFERENCES nodes(id),
  type    TEXT NOT NULL CHECK (type IN ('contains','references')),
  PRIMARY KEY (from_id, to_id, type)
);
CREATE UNIQUE INDEX one_parent ON edges(to_id) WHERE type = 'contains';

Three rules are enforced by the database itself, so no code path can break them:

  • Two live nodes cannot share a name (UNIQUE on qualified_name).
  • An arrow cannot point at a node that is not there (REFERENCES nodes(id), with foreign keys switched on).
  • A node has at most one contains parent (the one_parent index). The graph of contains arrows is a tree. The task itself speaks of a subtree, a root and a node's parent. An operation that would give a node a second parent is stored as rejected.

The journal

A deleted row is not thrown away. The delete moves it from the live tables into the journal tables, labelled with the delete's op_id. Undo later moves rows back one at a time and writes what it did next to each row.

ops
Every operation, with a running number, its op_id, its kind, the time it ran, whether a human or the ingest did it, and whether it was applied or rejected (with the reason). The running number is what "after the delete" means. Each undo is recorded here too, the first time it runs, as an operation of its own by a person (undo:<op_id>), so a later operation, or a redo, can tell what came after it. An undo or redo entry also stores the delete it is for, its round number and a finished mark (section 4, "Going back and forth").
removed_nodes
A copy of each node a delete removed: id, name, type, description, owner, tags, the id of its parent, and its place in parents-first order. For each of the three fields, and for the type, it also keeps who wrote it last and in which operation. Plus the columns undo fills in: outcome, reason, merged_into, waiting_on, the details the report prints for a merge, the undo that decided the row (decided_by), and for a merge what the live node held before undo changed it (prior), so a redo can put it back. Redo adds columns of its own: its outcome, its reason, and the redo that wrote them.
removed_edges
A copy of each arrow a delete removed, with its place in the order undo takes them. Plus outcome, reason, waiting_on, where the arrow points now if it was moved, and the undo that decided it. Redo adds the same columns of its own here.
field_writes
For each node and each of description, owner, tags and type: who wrote it last, and in which operation. This lets undo tell "empty because nobody wrote it" from "a person cleared it on purpose", and lets the type follow the same "most recent wins" rule.
edge_removals
Every arrow a person re-pointed away from its old target, with the number of the operation. Undo uses it so that it never puts back an arrow a person took away after the delete.

effective_tags is never copied into the journal. It is always worked out again from what is live at that moment.

3How undo works

Pick a story, then step through it. The first story is the usual case. Each of the others shows one rarer situation from start to end. The rules behind all of them follow below.

Story
Step

What undo does, in order

  1. Take the removed nodes of that delete from the journal, parents before children.
  2. For each node, decide one of three outcomes (next figure), make the change, put the arrow from its parent back, and refresh the tags of that node and everything below it. All of that is one transaction.
  3. Then take the remaining removed arrows (the references ones) and decide each one the same way.
  4. Then retry any rows of earlier undos that were waiting on this delete.
  5. Print the report from the journal rows.

Name clashes: two ids, one name

Every node has two identities. The id is for the machine and is never reused. The name is for people and only has to be unique among live nodes. A delete frees the name. The ingest then creates a node with that name and a fresh id. At undo time two nodes claim sales.orders: n2 in the journal and n7 in the live graph. Only one can be live.

The live node keeps its id and the old node is folded into it, field by field. A field is filled from the journal only if no person has written that field on the live node. Anything a person wrote after the delete stays as they wrote it. Each field lands in one of three situations:

  • Nobody wrote the field on the live node. It is filled from the journal. Example: the description of sales.orders.
  • A person wrote a different value. The person's value is kept. The journal value is not applied and is listed in the report under not_restored. Example: owner ben instead of asha.
  • A person emptied the field on purpose. It stays empty. This is why field_writes exists: an empty field that a person wrote is not the same as an empty field nobody touched. Example: the owner of the new sales.orders.email.

Description, owner and tags all follow this rule, and each one is treated as a whole value. For tags that means the two lists are never mixed: either the old list is filled in, or the person's list stays. Tags differ from the other two fields in one way only. They have a second layer, the inherited tags, and that layer is never filled or kept. It is recomputed. The last step of the usual case above shows every field of both merged nodes; the table below is the first of them.

All three situations are one rule: for each field, the value a person wrote most recently wins. Normally everything in the journal was written before the delete, and everything a person wrote on the live node came after it. So the person's value on the live node wins, and a field nobody touched is filled. The rule also settles the rare case where the journal holds the newer value, shown in the story "The recreated node is deleted again". A value that came with the seed counts as written at the very start. A value put back by an earlier undo counts from when a person first wrote it, not from when that undo ran. When the journal value wins over a value someone had written on the live node, the report lists the value it replaced under replaced, so nothing changes without showing up in the report.

type is not one of the three authored fields. It says what kind of thing the node is, such as table, view or column, and only ingest sets it. It follows the same idea with ingest as the writer: the type that ingest reported most recently wins. In a normal merge that is the type of the live node, and the report lists the old type when the two differ.

The old node is folded in. It is not brought back as a second node. Two live nodes cannot share a name, so a copy would need a different name, and the task's report has no outcome for that. A copy would also strand what undo is for: the description, owner and tags would sit on a node nobody uses, while the node that ingest keeps updating has none, and a tag such as pii would stop reaching the children. The cost is that the name is trusted. If a deleted name was reused for a different thing, the old values land on it. That is why only fields nobody wrote are filled, and why the report lists each one.

The live id stays because everything created after the delete already points at it: the arrows the ingest made, and any edit a person made. Every arrow that pointed at the old id is in the journal, so undo can re-aim those at the new id without touching anyone else's work. The mapping n2 → n7 is saved in removed_nodes.merged_into and used for the children and arrows that come after.

This gives mixed subtrees, and that is correct. sales.orders.total was not recreated, so it returns with its old id n4 under the new parent n7. The same rule applies whoever created the live node that holds the name. In this tool only ingest creates nodes. In the full system a person could also create one under an old name, and every field they filled in would be theirs and would stay.

Arrows

For each removed arrow, undo first works out where each end is now: the same node if it is live, the node it was merged into if it was merged, or nowhere if it was skipped or deleted since.

  • restored: both ends are live under their old ids. The arrow goes back as it was. Example: reports.daily → sales.orders.total.
  • merged, reason endpoint_merged: one end was merged, so the arrow is put back pointing at the node that took over. Example: reports.daily → n2 becomes reports.daily → n7.
  • merged, reason already_present: the same arrow already exists, because the ingest or a person made it. Nothing is added. Example: sales → n2 is already there as sales → n7.
  • skipped, reason endpoint_not_live: one end is gone. Example: someone deleted reports.daily after the first delete. The row records which delete holds that node.
  • skipped, reason child_has_other_parent: a contains arrow whose child now sits under a different parent. The later placement wins. Example: a person moved the new sales.orders under archive.
  • skipped, reason removed_by_person: a person re-pointed this same arrow away after the delete. A re-point is two changes by that person, one arrow removed and one added, and undo keeps both. Example: a person moved the arrow of reports.daily from the new sales.orders to sales.refunds.
  • skipped, reason would_create_cycle: a contains arrow that would make a node its own ancestor. Example: the ingest recreated two names with the parent and child swapped.

When a later delete is in the way

The command is undo <op_id>. The person names the delete they want back, so nothing forces the newest delete to be undone first. If an older delete is undone while a newer one still stands, some of its rows may need a node that the newer delete removed.

  • Such a row is skipped, with reason parent_not_live or endpoint_not_live. A node only disappears through a delete, so undo can always find which delete holds it. The row records that delete in waiting_on.
  • When that later delete is undone, its undo first handles its own rows. Then it retries every row of earlier undos that waits on it, parents first, by the normal rules.
  • A retried row keeps its single entry in the report of its own delete, with the outcome updated.
  • Each retried row is its own step, so a crash during the retries is resumed like any other.
  • Undone newest first, nothing ever waits.
  • The same holds for a node of this delete that came back once and was then deleted again by a later delete that still stands. The node belongs to that later delete now. This undo leaves it out: skipped, reason deleted_again, waiting_on the later delete. Undoing the later delete brings it back. This can only happen when the delete is undone a second time, after a redo (section 4).
  • Last, undo looks once more at its own rows that were skipped. If a retried row of an older delete brought the same node back in this undo, the row is marked restored, reason already_live, and its arrows are decided again. So a report never says skipped for something that is live.

The stories "A neighbour is deleted later" and "The parent is deleted later" show both cases.

When inherited tags are worked out again

One rule covers every case: inherited tags are never taken from the journal. After each step, undo recomputes effective_tags for the node it touched and for everything below that node as the graph stands now, inside the same transaction. The cases this covers:

  • A parent's tags changed while the node was deleted. A person added gdpr to sales after the delete. The restored sales.orders.total comes back carrying gdpr, which it never had before.
  • A merge puts tags back on a node that has children now. pii returns to sales.orders (n7). It flows to the restored total, to the recreated email, and to currency, a column that was created after the delete and was never part of it.
  • A person set tags on the recreated node. A person set the tags of the new sales.orders.email (n8) to ["hashed"]. Those stay and the old contact is not added back. Anything below n8 would inherit hashed, not contact. The report lists contact under not_restored, so a dropped tag is visible.
  • The recreated node sits somewhere else. If n7 is under a different parent now, it stays there. The old children restored under it inherit from the new place, not the old one.
  • A recreated node gets its old parent back. If n7 had no parent and the old contains arrow is put back onto it, n7 and its whole subtree are recomputed.
  • A node is skipped. Nothing changes, so nothing is recomputed.

Work done between the delete and the undo

Everything other people and the ingest did after the delete falls into one of three kinds. Each kind has one rule.

  • Independent. It touched something the delete did not. Example: adding gdpr to sales, rewriting the description of sales.refunds, or creating currency. Rule: left exactly as it is. Restored nodes pick up its effects.
  • Conflicting. It wrote something that undo would also write. Example: ben set the owner on the node that now holds the name sales.orders, and the journal says the owner was asha. The same goes for the new description and the new tags on sales.orders.email. Rule: the later human value wins, one field at a time. The old value is listed in the report and not applied.
  • Caused. It happened only because the delete happened. Example: the ingest created n7 because no live node had that name. Rule: treat it as the same thing coming back. Fold the old node into it, keep the new id, re-aim the old arrows.

Undo only adds rows and fills fields that no person has written since the delete. It never overwrites or removes anything a person did after the delete.

The same holds for edits that arrive while undo is running. Each step reads the live graph inside its own transaction, so an edit that lands between two steps is handled exactly like one that landed before undo began.

Crashes, resuming, and running it twice

  • One step, one transaction. A step is one removed node or one removed arrow. Its graph change, its tag refresh and its outcome in the journal are saved together or not at all.
  • Crash. With CRASH_AFTER=<n> set, undo counts every INSERT, UPDATE and DELETE it runs. On the n-th one the process stops at once, without saving the step it is in, as a killed process would. SQLite discards the half-done step when the file is opened again. Steps that finished before it stay saved, so CRASH_AFTER=1 saves nothing: the first write is inside the first transaction. Only undo and redo read the variable.
  • Resume. The next run skips every journal row that already has an outcome and carries on with the first one that does not. Each decision looks only at the live graph, so the resumed run makes the same decisions as an uninterrupted one.
  • A dump in between. A node goes in before its arrows, and the database refuses an arrow to a missing node. A dump taken after a crash shows a smaller graph that is still whole, with correct tags.
  • Run it twice. The second run finds an outcome on every row, writes nothing, and prints the same report.

How long undo stays available

The rules above give a correct result however much time has passed. More edits only mean more rows come back as merged or skipped. What gets worse with time is how much of the result the person asking can predict.

The scenario gives one measured rate: several hundred edits in twenty minutes around a delete of 10,000 nodes. Taking 300 edits, that is 15 a minute.

The last column is a ceiling. It assumes every edit lands on a different deleted node. At twenty minutes nearly everything comes back as it was. After about one working day of edits there are as many edits as deleted nodes. From there undo no longer takes back one action. It merges a day of other people's work with an old copy of 10,000 nodes, and the report is too long for a person to review.

The limit is 24 hours after the delete. A full day on the clock holds about one working day of edits, and it covers the usual late case: deleted in the evening, noticed the next morning. The value is subject to experimentation, because it rests on the one rate the scenario gives.

  • Checked when undo starts. Undo compares the current time with the time the delete was applied, stored in ops. Past 24 hours it refuses, changes nothing, and says why. The journal rows stay where they are.
  • An undo that has started can always finish. A crashed run is resumed and a finished run prints its report again, whatever the clock says. Otherwise a crash close to the limit would leave the graph half restored.
  • The command-line tool does not enforce it. The task puts retention out of scope, the operations in the fixture carry no real clock, and the checks expect undo to run on the fixture whenever it is called. The limit belongs to the full system.

4How redo works

Redo is the one extension the task names. It is built as a fifth command next to the task's four, and this section is its design. Undo already records most of what redo needs: which undo decided each row, and what a merged node held before. Redo adds a round number and a finished mark to the entries in ops, and columns for its own outcome to the journal rows.

redo <op_id> takes the op_id of a subtree delete that has been undone, and applies the delete again to the graph as it is now. It does not replay the delete from scratch. It takes back what the undo put back: restored nodes go out again, the arrows undo added are removed, and the fields undo filled get the value they had before. Like undo, it never removes or changes anything a person did in the meantime. For redo, "in the meantime" means after the undo.

Pick a story, then step through it. Each one starts where an undo left the graph.

Story
Step

What redo does, in order

  1. Record the redo in ops as an operation of its own. A repeated or resumed run finds the entry and does not add another.
  2. Take every row of this delete: each node and arrow the delete removed, whichever undo command put it back. Add the rows of other deletes that an undo of this delete retried and put back.
  3. For each node undo merged, put back the fields undo filled, then refresh the tags of the live node and everything below it. Merges go first, because a merge can sit on a node that the next step takes out.
  4. From both sets, take the nodes undo restored, children before parents. For each one decide removed or kept (next figure). A removed node goes back into the journal together with every arrow that touches it. That is one transaction.
  5. Take the remaining arrows undo added, the ones between nodes that stay, and remove them.
  6. Go through the rows that are left: a node undo skipped, and an arrow undo skipped or found already there. Nothing changes in the graph for these. They are reported as unchanged.
  7. Mark the redo finished and print the report.

Each step also resets the row it handled, in the same transaction. A row redo kept keeps its outcome. Every other row is opened again: it has no outcome, as it was right after the delete. "What each row goes back to" below gives the rule.

The order is undo's order turned around. Undo goes parents first, because a child needs its parent to attach to. Redo goes children first, because a parent can only leave once nothing is left under it.

Taking a restored node out again

A node undo restored is removed again when both of these hold. Otherwise it is kept, and the report gives the reason.

  • No person has written it since it came back. field_writes holds the number of the last write to each field, and the undo has a number of its own in ops. A write by a person with a larger number came after the undo. Reason when it fails: written_since_undo.
  • Nothing else is attached to it. Every child and every arrow that touches it must be one this redo is taking out as well. A node created or moved under it since, an arrow a person or the ingest added to it since, a child that was itself kept, or a row of another delete that its own undo put there, all keep it in place. So does another undo that still stands and worked on this same node after it came back: it merged an old node into it, or it found the node live and counts it as restored for its own delete. Removing the node would take that undo's result away with it. Reason: still_in_use.

A removed node goes back into the journal of its delete, and its name is free again. The journal copy is refreshed from the live node as it leaves. If the ingest reported a new type for the node while it was back, that type is not lost. A write by the ingest does not keep a node in place: it only happened because the node was there, and the next ingest run recreates the node if the source still has it.

Putting filled fields back

When undo merged an old node into a live one, it filled some fields of the live node and saved what they held before in prior: the value, and who wrote it and when. Redo goes through the filled fields one at a time:

  • The field is still as undo left it. Redo puts back the earlier value and the earlier write record. Most of the time the earlier value is "empty, nobody wrote it". Example: the description and the tag pii on the new sales.orders.
  • A person has written the field since the undo. It stays as the person wrote it. Reason: written_since_undo.

Undo copied the old write record along with the value, so "still as undo left it" is a plain comparison: the field's write record is still the one undo copied. Fields undo did not fill were never touched and are not touched now. Inherited tags are recomputed, as always: when pii leaves the live node, it leaves everything below it.

Arrows

  • removed: undo added the arrow, and it goes out again. This covers an arrow that touches a removed node, and an arrow undo re-aimed at a node that stays. Example: reports.daily → n7.
  • kept, reason end_kept: the arrow touches a restored node that redo kept. A node that stays keeps the arrows undo gave it, so it is not left half connected.
  • unchanged, reason not_added_by_undo: undo found the arrow already there, or skipped it. There is nothing to take out of the graph.
  • unchanged, reason changed_since_undo: someone re-pointed the arrow away after the undo. Whether it is there now or not is their doing, so redo leaves it as it is.

When an arrow undo added touches one node that leaves and one that stays, the arrow leaves: an arrow cannot point at a missing node. It is kept only when neither end leaves.

A node undo skipped is reported the same way: unchanged, reason not_restored_by_undo.

What each row goes back to

Redo changes the graph, and it also resets the journal rows, so that the journal says again that the delete stands. After redo, every row of this delete that the undo decided is in one of two states:

  • Kept. The node or arrow is still live because redo kept it. The row keeps the outcome undo gave it, because that outcome is still true.
  • Open. Every other row has no outcome and no waiting_on, as it was right after the delete. This includes the rows where redo changed nothing in the graph: a node or arrow undo skipped, an arrow undo found already there, a merge that filled nothing, and an arrow someone moved away since.

The rows that needed no change in the graph are opened too, for two reasons:

  • A skipped row must stop waiting. A row skipped with waiting_on: d2 comes back when d2 is undone. If redo left it waiting, a later undo of d2 would restore part of a delete that was redone. The story "Redo while rows were waiting" shows this.
  • A later undo must decide every row afresh. Example: undo merged the old sales.orders.email into n8 and filled nothing. After the redo, someone deletes n8. If the row still said "merged into n8", the next undo of d1 would pass over it. But its name is free and its parent is live, and that is exactly the node an undo must restore.

One kind of row is not opened. A row of another delete that an undo of this delete retried goes back to skipped, waiting_on this delete. That is what it was before the undo, and its own delete is still undone. The report lists these rows apart from the delete's own rows, under other_nodes and other_edges, each with the delete it belongs to.

When a later delete got there first

Between the undo and the redo, a person can delete something undo put back. It is then in the journal of that later delete, here d3. Redo never takes back a person's delete, and never edits the journal of another delete.

  • A node undo restored is already gone. Example: undo d1 restored sales.orders.total, then d3 deleted it on its own. Redo d1 has nothing to remove. Outcome unchanged, reason deleted_since, and the report names d3. The row is opened like the others. Its journal copy is refreshed from the copy d3 holds, so the journal of d1 has the node as it last was.
  • The node undo filled is already gone. Example: undo d1 filled the description of n7, then d3 deleted n7. Redo cannot put the field back, because n7 is not in the graph. Outcome unchanged, reason target_not_live, naming d3. The copy of n7 in the journal of d3 keeps the filled value. An undo of d3 has to bring n7 back with the fields it had when d3 removed it, so that copy is left as it is.
  • An arrow undo added is already gone, because d3 removed one of its ends. Outcome unchanged, reason deleted_since.

Such a node belongs to the later delete now. A new undo of d1 does not bring it back, because that would take back d3, which someone did afterwards. Its row is skipped, reason deleted_again, waiting_on: d3, by the same rule as "When a later delete is in the way" in section 3. Undoing d3 brings the node back, and the retry then marks the row of d1 as restored, reason already_live: the node is live under its own id and there is nothing to add. The small fixture has a test for the first case.

Work done between the undo and the redo

The same three kinds as for undo, each with one rule.

  • Independent. It touched something undo did not put back. Rule: left exactly as it is.
  • Conflicting. A person wrote on, or attached something to, a thing undo put back. Example: a person rewrote the description of the restored sales.orders.total. Rule: that thing stays, with everything it needs to stay whole: its parents and its arrows. The report lists it as kept.
  • Caused. It happened only because the undo happened. Example: the ingest found sales.orders.total live again and updated its type instead of creating a new node. Rule: it does not hold redo back, and the journal copy keeps the newer type.

Redo only takes back rows undo decided, and only while they are as undo left them. It never overwrites or removes anything a person did after the undo.

Redo, undo, and their order

  • Redo straight after undo gives back the graph from before the undo. Nothing has changed in between, so every row is taken back. The dump is the same, byte for byte, as the dump taken just before the undo. There is one exception. If an earlier redo had to keep a node, and what kept it has gone since, this redo takes that node out too. Example: the first redo kept sales.refunds because the ingest had added an arrow to it, and that arrow has since been deleted. Redo means "delete what the delete removed", so the node leaves now, although this undo did not put it back.
  • Undo can run again after a redo. Every row redo did not keep is open, so undo decides it like a new row, against the graph of that moment. With nothing changed in between, it gives the same graph as the first undo.
  • A new undo checks the rows redo kept. A kept row still says restored, and that can have stopped being true: the kept node was deleted again, or a kept arrow was moved away. Before deciding anything, undo opens every row of the delete that says something is in the graph when it is not, and decides it again by the normal rules. So the report of every undo is true for the graph it leaves. The first undo of a delete has no such row.
  • A redone delete stays redone. Redo opens the rows that were waiting on another delete. Undoing that other delete later does not bring them back. Only a new undo of this delete does.
  • Only an undone delete can be redone. For a delete that was never undone, for any other operation, or for an id that does not exist, redo prints an error and writes nothing.
  • Redo d1 takes out what d1 removed, whichever undo command put it back. A node of d1 that waited and was restored later by the undo of d2 is still a row of d1. So the result does not depend on which undo ran first. The story "The parent was deleted later" shows this.
  • After several undos, redo the newest undo first. If an older undo is redone while a newer one still stands, some of its nodes may carry children or arrows that are rows of the newer undo's own delete, or may hold fields the newer undo merged in. Those nodes are kept, reason still_in_use. Redone newest first, nothing is kept for this reason. This mirrors undo, where the newest delete undone first means nothing waits.

Going back and forth

A person can undo, redo, undo again and redo again. One undo and the redo that follows it is a round.

  • Each undo and each redo has its own entry in ops. The entry stores which delete it is for and which round it is, as values of their own. Its name (undo:d1, redo:d1) is only a label, and nothing is read out of it, so a delete with an unusual op_id cannot be mixed up with a round. A journal row points at the entry that decided it by the entry's running number, so "since it came back" always has an exact meaning.
  • Repeat or new round. The same command can mean two things, so the tool looks at the newest undo or redo entry for the delete. For undo d1: with no entry, this is the first undo. If the newest entry is an undo, this call repeats or resumes it, so a finished undo writes nothing. If the newest entry is a redo, a new round starts. For redo d1: with no undo entry, it is an error. If the newest entry is an undo, this is the redo of that round. If the newest entry is a redo, this call repeats or resumes it.
  • Each entry is marked finished when its last step is saved. redo refuses while the undo of the same delete is unfinished, and undo refuses while its redo is unfinished. The tool says which command to run again first, and writes nothing. A crashed run is always finished by running the same command again.
  • A redo outcome names the redo that wrote it. A redo skips only the rows that carry its own mark, and decides a row marked in an earlier round again. So a node that came back in a new round can go out again, and a node an earlier redo kept is looked at again.

Crashes and running it twice

  • One row, one transaction, as for undo. The graph change, the tag refresh, the row's redo outcome and the reset of its undo outcome are saved together or not at all.
  • Each journal row gets a redo outcome in columns of its own: removed, kept or unchanged for nodes and arrows, and reverted for a merged node, with a reason. An opened row loses its undo outcome and keeps its redo outcome. The report is a printout of the redo outcomes.
  • Crash and resume. CRASH_AFTER=<n> works for redo as it does for undo. A resumed run skips every row that already has an outcome from this redo.
  • Run it twice. The second run finds the redo marked finished, writes nothing, and prints the same report.

What the checker tests

  1. No change made by a person after the undo is lost or altered by the redo. Tested like check 1, with a dump just before the redo and one just after.
  2. Redo straight after undo gives the dump from before the undo, byte for byte. A second undo then gives the dump from after the first undo.
  3. The report has one entry for every node and arrow the delete removed, exactly once, as undo's report does. Each outcome agrees with the dump: a removed row is gone, a kept row is there, a reverted field holds its earlier value.
  4. Two rounds give the same two graphs. Undo, redo, undo, redo with nothing in between: the dumps after both undos are the same, and the dumps after both redos are the same, byte for byte.
  5. An undo after a redo passes checks 1 to 5 of a first undo. One addition: a node that a later delete removed again is not expected back, and must not come back.
  6. An unfinished command blocks the other one. A redo after a crashed undo, and an undo after a crashed redo, print an error and leave the dump as it was.
  7. The graph stays whole. No two live nodes share a name, no arrow points at a missing node, and inherited tags are correct.
  8. A redone delete stays redone. After a redo, undoing another delete brings back no node or arrow of this one. Tested with the story "Redo while rows were waiting": undo d1, redo d1, undo d2 must end with sales and sales.refunds back and sales.orders still deleted.
  9. Redo is idempotent and resumable, tested as checks 6 and 7 are for undo.

For every redo the checker works from the dump just before it, the dump just after it and its report. Where one delete was undone it also works out, on its own, the graph the redo must leave: what undo put back is the difference between the dumps around the undo, and each node of it must leave unless a person wrote on it since, an arrow undo did not add touches it, or a child that undo put back stays. The dump after redo has to equal that graph.

On the main fixture the run script redoes the delete straight after the undo, redoes it a second time, undoes it again, lets people and the ingest change a few of the restored nodes, and redoes it once more. It also crashes the redo at ten points and tries each command while the other is unfinished.

Each redo story above is a test in the small fixture, the same way the undo stories are, and so are the three cases of "When a later delete got there first" and "Two undos on one node". One more story covers a node that redo kept and a later delete then removed. That makes fourteen redo runs. They use three more operations files (the delete alone, the delete with one recreated node, and a column that is deleted, recreated and deleted again) and four small files that are applied between an undo and a redo.

The eight checks and what makes each one hold

  1. No human change after the delete is lost. Undo only inserts rows and fills fields with no human write since the delete, read from field_writes. The checker proves it by comparing a dump taken just before undo with the dump taken after: every value a person wrote is unchanged, every arrow a person added is still there, and no arrow a person moved away has come back.
  2. Free name and live parent means restored. This is the node decision in the figure above. The task says the parent must be live "at undo time". Here that means: live once undo has dealt with the parent, whether the parent was restored or was merged into the node that holds its name. The checker uses the same reading. From its own replay it works out which removed names are free and which parents are live, and expects each such node in the dump after undo with its old id, description, owner and tags.
  3. No two live nodes share a name. A clash becomes a merge before any insert, and the UNIQUE rule on the table backs it up. The checker counts the names in the dump after undo.
  4. The report covers every removed node and arrow once. The report is a printout of the journal rows of that delete. Each row has exactly one outcome. The checker builds the list of removed nodes and arrows from its own replay and matches it against the report: nothing missing, nothing twice. It also holds each outcome against the dump: a restored row is there under its old id, a merged row points at a live node, a skipped row is absent.
  5. Inherited tags are correct. They are recomputed from the live graph inside every step. The checker recomputes them from the own tags and the contains arrows in the dump, and compares.
  6. Running undo twice gives the same dump. The second run has no row left to decide, so it writes nothing. The run script runs undo again, and the checker expects the same dump and the same report, byte for byte.
  7. A crashed undo can be finished. One transaction per step, and foreign keys rule out arrows to missing nodes. The task does not say which n, so it has to hold for any. The run script copies the database after apply and runs a clean undo on one copy and crashed undos on others: at the first write, at a few in the middle, at the last, at a number larger than the total, and with two and three crashes in a row. The checker compares what they left.
  8. Under 60 seconds. The scenario is about 5,000 rows and a few thousand small transactions. The run script times the scenario and the whole run, and the checker fails if either goes over. The work grows in step with the number of removed rows, one small transaction each, so the 10,000-node case follows the same path.

The fixture

The fixture is the test data. gen_fixture.py writes it from a seed number, and the same seed always gives the same files.

The starting graph: about 5,000 nodes and edges.
ops.jsonl
The operations, in order. First, one subtree delete of at least 500 nodes. Then about 300 operations of mixed kinds.
planted.json
Which nodes each planted case below uses, so the checker can find each case and test it. The eight checks do not use it.

The seed holds no inherited tags. They are worked out when the seed is loaded. An ingest line carries no id, because the tool makes it. Since that id follows from the op_id and the name, the generator can work it out too and use it in later lines, as op31 does with n7.

The task sets minimums for those operations. After writing the files the generator counts each one, prints the counts, and stops with an error if any is not met:

  • The delete removes at least 500 nodes.
  • People edit nodes next to the deleted area: its parent, its siblings, and nodes that referenced it.
  • Edges are re-pointed to other nodes.
  • An ingest run recreates at least 50 of the deleted names under new ids.
  • People edit at least 5 of those recreated nodes.

Random data alone might never reach a rare rule, so the generator also plants one case for each of these:

  • A recreated node that nobody edited. Its three fields are filled from the journal.
  • A recreated node where a person changed a field. The person's value is kept.
  • A recreated node where a person emptied a field. It stays empty.
  • A recreated node that a person moved under another parent. The old parent arrow is skipped.
  • A deleted name that was not recreated, under a parent that was. It is restored with its old id under the new parent.
  • A recreated child whose parent name was not recreated. It gets its old parent back.
  • A reference that a person re-pointed onto a recreated node. The old arrow is counted as already present.
  • A reference that a person re-pointed away from a recreated node. The old arrow is skipped.
  • A recreated node whose type differs from the old one. The newer type stays and the report lists the old one.
  • A tag that a person added above the deleted root. Restored nodes come back carrying it.
